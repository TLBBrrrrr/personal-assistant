> 这是一份**前瞻性设计文档**，不是当前系统的一部分。它讲的是一个和「记录系统」完全不同的东西。

## ⚠️ 先分清：这不是你现在的记录系统

| | **记录系统**（`02-记录系统设计.md`，已实现） | **AI 记忆系统**（本文档，未实现） |
|---|---|---|
| 给谁用 | **用户自己** | **AI Agent** |
| 目的 | 把发生过的事存成个人档案，供用户查、回顾、总结 | 让 AI 越来越懂用户、跨会话少犯错、自动提炼规则 |
| 存什么 | 带时间、情绪、原文的生活事件流水 | 提炼后的稳定事实、验证过的规则、结构化知识页 |
| 典型问题 | "我昨天做了什么？" "关于跑步记了什么？" | "AI 知不知道我喜欢晨跑？" "它会不会重犯上次的错？" |
| 价值来源 | 档案本身对用户就有价值，与 AI 无关 | 只在 AI 用它改善行为时才有意义 |
| 当前状态 | 核心已跑通 | **一行代码都没有** |

**一句话**：你的 EventStore 是「写给自己的日记」；这里的记忆系统是「给 AI 看的说明书」。两者数据、目的、生命周期都不同，不要混为一谈，也不要把 EventStore 叫成"记忆"。

本文档的用途：将来某天你决定"我要让助理更懂我"时，照着这里评估、设计、实现。**现在不需要做。**

## 1. 要不要做？先看清醒的证据

在投入之前，必须知道一个不那么好听的事实：**记忆系统不是越多越好，甚至常常不如朴素的"把全部历史塞给模型"。**

两个来源的结论：

- **Anthropic 官方博客《The components of agent memory》(2026-11-06)**：记忆让 Claude 在 CL-Bench 数据库任务上从 0.655 提升到 0.838；但宝可梦实验里，"什么都记"的 Sonnet 3.7 写了 **413 个文件**只得 1 枚徽章，"少而精"的 Fable 5 只写 **9 个文件**却拿 4 枚徽章。
- **CL-Bench 原始论文（arXiv 2606.05661，UC Berkeley + Snorkel AI，非 Anthropic）**：朴素的 full-context ICL 反而打败大多数专门记忆系统，最好的系统也只有 **25.4%** 增益；累积的状态经常帮倒忙（stale beliefs、错误泛化）。

合起来的信号很一致：**价值不在"存了多少"，而在"写进去的东西质量 + 有没有纠错机制"。** 所以下面所有设计都围绕这两个核心。

**启用判断**：先用自己的记录系统真实用一段时间。只有当出现明确痛点——比如"它总记不住我偏好""同样的错犯了好几次""每次都要重复交代背景"——才值得做记忆系统。没有痛点就不要做。

## 2. 核心理念：记忆是对未来的预测

Anthropic 的关键提法：**写下一记忆 = 预测未来会用到它。**

- 写下"用户喜欢晨跑" = 预测未来会话会依赖这个事实
- 写下"查这类问题要先看 X 表" = 预测这个规则下次还成立

强模型会形成学习闭环：**失败 → 记下 → 提假设 → 验证 → 提炼成规则**。CL-Bench 里 Opus 5 是第一个自发跑完整套的模型；早期模型只写笔记不回头看，等于"记了本没人翻的日记"。

**设计启示**：存的东西必须是"对未来有用"的判断，不是流水账。每条记忆最好带：它是什么、为何可信、适用边界。

## 3. 架构：四层 + 离线整理

参考 Anthropic 的四层模型（自下而上，token 逐级压缩）：

| 层 | 名字 | 作用 | 你项目里的对应物 |
|---|---|---|---|
| ① | **Transcripts** 原始日志 | 可搜索的原始过程记录，是一切的地基和纠错基准 | ≈ 已有的 EventStore / events.db（但需保留原始层级） |
| ② | **Memory notes** 记忆笔记 | AI 判断显著后写下的短笔记：失败、规则、验证结果、陷阱 | 无（`memory/` 空目录接口预留） |
| ③ | **Memory representations** 知识表征 | 结构化、互链的页面（wiki），形成心智地图 | 无 |
| ④ | **Injected context** 注入上下文 | 每次会话前预加载的少量高价值内容 | 无（你有过"首轮锚点/摘要"设想） |

**关键点**：你的记录系统已经提供了第 ① 层（原始日志）——这是地基，而且是纠错必需的 ground truth。所以真要做记忆系统，不是从零开始，而是在事件档案之上加 ②③④ 层。

### 3.1 dreaming（离线整理）——最值得借鉴的机制

类比人睡眠时海马体重放经验：在会话间的空闲时间，回看原始日志，做五种整理：

1. **纠错**：对照原始日志修正错误记忆（宝可梦里记错传送门位置，dreaming 纠正后脱困）
2. **提炼规则**：把验证过的经验固化成规则，附"为何为真"
3. **构建 / 维护知识表征**：建 wiki 页、合并重复、修断链
4. **上提 / 降级**：把重要笔记上提到注入层，细节降级为链接
5. **跨会话补缺口**：发现多个会话的共同模式、补齐遗漏

**为什么值得**：实时写记忆会分散 AI 注意力，而且当下写的内容可能出错或过时。dreaming 把整理推到后台，用"向后看"修正"向前走"的偏差。

### 3.2 注入层要极度克制

- Claude Code 的做法：只加载 `MEMORY.md` 前 **200 行 / 25KB**，作为**索引**告诉 AI "它知道什么、去哪找"，细节按需检索。
- 原因：注入的内容占 token；错误一旦进注入层会被带进每个会话；过长的指令文件反而降低遵循度。

## 4. 从论文提炼的设计原则

| 原则 | 依据 | 落到你项目该怎么做 |
|---|---|---|
| **少而精 > 什么都记** | 413 文件输给 9 文件 | 宁缺毋滥；写之前判断"未来真会用吗" |
| **别存可观察到的状态** | 游戏里"当前多少钱"每帧可读，存了是冗余 | 日程、天气、当前状态这类会变/可查的，不进记忆 |
| **告诉 AI 用途，不写死规则** | "只记失败"这条规则让 Opus 5 增益 -0.234 | 给高层指引，让模型自己判断显著性 |
| **记忆要可纠错** | dreaming 纠错后 AI 才能脱困 | 每条记忆保留 `source_ref` 指向原始事件，供核对 |
| **存规则 + 为何为真 + 陷阱** | Opus 5 的完整闭环笔记结构 | 记忆条目别只存结论，带上依据和边界 |
| **注入层当索引** | 200 行 / 25KB 上限 | 顶层只放目录和关键规则，细节按需取 |
| **地基是原始日志** | 论文结论：transcript search 是 memory 基础 | 保护好 EventStore 的原始流水，别只留摘要 |

## 5. 未来若实现，建议的落地顺序

> 以下都是**尚未实现**的设想，按性价比排序。不做也可以，系统照样能用。

**第一步：给事件加"可信度"维度**（成本最低）
- Event 模型加 `confidence` / `validated` / `source_ref` 字段
- 区分"用户明说的稳定偏好"和"AI 的一次猜测"
- 这是后续一切提炼的基础

**第二步：轻量 dreaming**（最高价值）
- 定时任务：定期扫描新事件 → 提炼规则 → 写记忆笔记 → 纠错
- 对照原始事件核对，避免错误固化
- 注入层保持小

**第三步：wiki 主题页**（解决"按主题回忆"的体验）
- 按人 / 主题建页（如"跑步"、"张三"），聚合相关事件 + 规则 + 互链
- 论文里 wiki + search 把成绩从 54% 提到 61%，且每问题省约 2 万 token

**第四步：注入层索引**
- 一个 200 行以内的索引文件，每次会话加载
- 细节按需检索，不全量塞

**关于 mem0**：早期设计里 Phase 1A 是接 mem0 做事实记忆。现在看，**不急于接**——先把记录系统用起来，确认痛点后再决定用 mem0 还是自研轻量方案。CL-Bench 里 mem0 的表现并不突出。

## 6. 接口预留（当前为空壳）

```python
# memory/ —— 目前目录为空，仅此协议占位
class MemoryStore(Protocol):          # AI 事实/规则记忆，非事件档案
    async def add(self, user_id: str, memories: list[dict]) -> None: ...
    async def search(self, user_id: str, query: str, limit: int = 5) -> list[dict]: ...
    async def forget(self, user_id: str, memory_id: str) -> None: ...
```

注意：`memory/` 与 `recall/`（事件档案）是两个独立模块，物理和逻辑都分开。将来它们之间的唯一联系，是记忆系统可以**读**事件档案作为原始素材——单向依赖，不反向写。
