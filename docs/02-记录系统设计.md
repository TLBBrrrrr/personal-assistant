# 记录系统设计

> 版本 v1.3 · 2026-11-23 · 状态：**Phase 1B 已实现并验证**（随口记 + EventStore 落库 + 四种回忆）；**Phase 2 已用 Garmin 官方 Personal API 真实同步验证**（SQLiteMetricStore + 11 类抓取器 + 独立同步/查询脚本）；TimeAligner / Digest / 向量检索仍为预留
>
> **这是本项目的核心子系统，服务于用户自己**：把发生过的事记下来，之后能查、能回顾、能总结。
>
> ## ⚠️ 一条必须遵守的边界
>
> **本系统是「记录系统」，不是「AI 记忆系统」，两者完全无关。**
>
> - **记录系统（本文档）**：用户自己的**个人档案**。存"发生了什么"，给用户查、回顾、总结。它不关心 AI 是否变聪明——哪怕没有大模型，这些档案对用户依然有价值。
> - **AI 记忆系统**：让 AI 越来越懂用户的机制（稳定偏好、自动提炼规则、离线整理等）。**尚未实现**，当前不展开。
>
> 不要用"记忆""长期记忆""记忆层"来称呼本系统的任何部分。EventStore 存的是**事件档案**，不是"记忆"。
>
> 变更历史：v0.2 客观运动数据与主观生活感受分开存；v0.3 落地 Phase 1B；v1.0（本次）从"记忆与记录"拆出，成为独立的记录系统文档，剥离所有 mem0 / 记忆分层内容。

## 1. 定位：记录什么，怎么分

这个系统要记的是**两类本质不同的东西**，必须分开存：

| 类别 | 内容 | 谁产生 | 特征 | 存储 | 现状 |
|---|---|---|---|---|---|
| **A. 主观生活事件** | 经历、感受、想法、决定、人际 | 人（对话中表达） | 语义化、低频、量小、需回溯 | **EventStore（事件档案）** | ✅ 已实现 |
| **B. 客观运动数据** | 佳明活动、睡眠、心率、步数、体重 | 机器（Garmin） | 结构化、高频、量大、字段固定 | **MetricStore（SQLite 业务表）** | 接口预留 |

### 为什么 A 和 B 必须分开

| 维度 | B 客观运动数据 | A 主观生活事件 |
|---|---|---|
| 产生方 | 机器自动同步 | 人主动表达 |
| 结构 | 字段固定，可聚合统计 | 自由文本，需语义检索 |
| 频率量级 | 每天几十条 | 每天几条 |
| 索引方式 | 时间 + 类型 + 数值范围 | 全文 + 标签 + 情绪 |
| 清理策略 | 原始数据可定期归档 | 长期珍藏 |
| 向量化 | 没必要，浪费 | 需要（未来），支撑语义检索 |

塞进一个流水里的后果：海量运动数据淹没生活感受、无意义的向量化开销、清理策略互相绑架。**分开存是明确的决定。**

但"分开"不等于"老死不相往来"——有个典型需求：把客观数据和当时感受在时间轴上对上，比如"上次跑 10 公里那天我感觉怎么样"。这靠 **TimeAligner 时间对齐**桥接（第 5 节），而不是把两类数据混存。

### 和"AI 记忆系统"的边界（务必分清）

| | 记录系统（本文档） | AI 记忆系统（05 文档，未实现） |
|---|---|---|
| 服务对象 | **用户自己** | **AI Agent** |
| 回答的问题 | "发生过什么？我当时怎么想？" | "AI 记住了用户的什么偏好/规则？" |
| 数据 | 带时间、情绪、原文的事件流水 | 提炼后的稳定事实、规则、知识页 |
| 有没有价值 | 独立于 AI，档案本身就值钱 | 只在 AI 用它变聪明时才有意义 |
| 当前状态 | 核心已跑通 | 未实现，可选 |

## 2. Event 数据模型（核心）

### 2.1 结构定义

```python
from datetime import datetime
from pydantic import BaseModel

class Event(BaseModel):
    id: str                      # 唯一 ID
    occurred_at: datetime        # 事件发生时间（不是记录时间）
    recorded_at: datetime        # 写入系统的时间
    source: str                  # 来源：dialogue | manual | digest | system
    type: str                    # 类型：experience | feeling | note | decision | milestone | summary
    title: str                   # 一句话标题，"跑完10公里很畅快"
    content: str                 # 正文，自然语言的经历/感受描述
    tags: list[str]              # 主题标签，["跑步", "心情", "工作"]
    entities: list[str]          # 相关实体，["同事张三", "项目X"]
    mood: str | None             # 情绪标签，可选，"开心" | "疲惫" | "平静"
    importance: float            # 0-1，重要度，驱动总结筛选
    metric_refs: list[str]       # 关联的客观数据 ID（可选，时间对齐时生成）
    embedding_ref: str | None    # 向量库引用，语义检索用（未接）
```

字段设计的几个关键取舍：

- **source 不含 garmin**：佳明数据不进事件档案，它进 MetricStore。事件里只用 `metric_refs` 留一个关联指针。
- **不存 payload**：结构化原始数据属于 MetricStore，不在事件里存第二份。
- **occurred_at 与 recorded_at 分开**：补记、导入历史数据时两者不同，回忆按 `occurred_at` 走。
- **mood 显式建模**：感受类事件的高频查询维度，比纯文本检索直接。
- **importance 驱动总结**：未来生成周/月报时优先取高重要度事件，避免流水账。
- **embedding_ref 预留**：语义检索（"那次很累的跑步"）用，目前未接，当前靠关键词 + 标签。

### 2.2 当前物理存储

`data/events.db`（SQLite，默认路径，可配）：

| 存储 | 内容 | 技术 | 状态 |
|---|---|---|---|
| `events` 表 | 事件全部结构化字段 | `sqlite3` | ✅ |
| `events_fts` 虚拟表 | 关键词检索 | SQLite FTS5 | ✅（中文以 LIKE 为主、FTS5 为辅） |
| 时间 / 类型索引 | 时间线与类型过滤 | SQLite 索引 | ✅ |
| 向量库 | 语义检索 | 本地向量库 | 预留未接 |

`EventStore` 接口（同步方法供 CLI / hook / 工具直接用，async 方法兼容既有 Protocol）：

```python
class SQLiteEventStore:
    def add(self, event: Event) -> str: ...
    def update(self, event_id: str, patch: dict) -> bool: ...
    def get(self, event_id: str) -> Event | None: ...
    def delete(self, event_id: str) -> bool: ...
    def find(self, query: str, time_range=None, tags=None, limit=10) -> list[Event]: ...
    def by_tag(self, tag: str, time_range=None) -> list[Event]: ...
    def timeline(self, start, end, page=0, size=50) -> list[Event]: ...
    def similar_exists(self, title: str, within_hours=24) -> bool: ...
    def stats(self) -> dict: ...
```

查看数据库：`python3 scripts/view_db.py`（支持 `-k` 关键词、`-v` 正文、`--sql` 自定义查询）。

## 3. 自动记录机制（随口记）

你选的是"对话随口自动记"——不用下指令，聊着聊着就存了。

### 3.1 写入路径

```
用户说话 → Agent 回复 → [post-turn hook]
                          ├─ 判定：这轮有没有值得记的经历/感受？
                          ├─ 否 → 不记（寒暄、知识问答、指令）
                          └─ 是 → 抽取成 Event
                                  ├─ LLM 结构化输出 + Pydantic 校验
                                  ├─ 相对时间解析（昨天/上周/3天前 → occurred_at）
                                  ├─ 去重（同标题 24h 内已存在则跳过）
                                  └─ 落库 → events.db
```

### 3.2 关键设计（已验证）

- **保守判定**：系统提示词明确区分"值得记"（经历 / 感受 / 决定 / 计划 / 带时空人物的事实）和"不记"（寒暄 / 知识问答 / 助理自己说的话 / 高度重复）。实测"你好"不产生事件。
- **结构化输出**：用 PydanticAI 的 `output_type=ExtractionResult`，模型直接吐 `EventDraft` 列表，Pydantic 校验，不解析自由文本。
- **时间解析**：`resolve_when()` 把"昨天 / 前天 / 上周六 / 3天前 / X月X日"解析成 `occurred_at`，以当前时间为参考。
- **去重**：同标题 24 小时内已存在则跳过。
- **失败隔离**：抽取器内部吞掉所有异常，post-turn hook 再包一层——模型出错绝不影响主对话。
- **可关闭**：`ASSISTANT_AUTO_RECORD=false` 可关，调试用。

**值得记**：经历、决定、计划、情绪感受（泛生活，不限运动）；带具体时间 / 地点 / 人物的事实；里程碑事件。
**不记**：纯知识问答、寒暄、助理自己说的话、高度重复内容。

### 3.3 客观数据写入路径（接口预留）

佳明数据同步后写**独立的指标表**，不生成事件：

```
Garmin 同步 → sport 适配器 → 结构化数据 → MetricStore（Activity/Sleep/DailyMetric）
                              └─ 不向量化、不进 EventStore
```

两套 emitter 各司其职：`MetricEmitter` 处理机器客观数据，`EventEmitter` 处理人的主观表达。

## 4. 四种回忆方式（已实现 + 预留）

| 需求 | 检索路径 | 落地工具 | 状态 |
|---|---|---|---|
| **随时问随时查** | 关键词（LIKE + FTS5）+ 时间过滤 | `recall_search` | ✅ |
| **按主题回顾** | 按 `tags` / `entities` 过滤 | `recall_topic` | ✅ |
| **时间线浏览** | 按 `occurred_at` 排序分页 | `recall_timeline` | ✅ |
| **看统计** | 按 type / 时间聚合 | `recall_stats` | ✅ |
| **定期自动总结** | 聚合事件 + 指标 → LLM 归纳 → Digest | `digest(period)` + 定时任务 | 预留 |
| **语义检索** | 向量相似度（"那次很累的跑步"） | 本地向量库 | 预留 |

四个工具都注册进 Agent，对话里直接问就触发。实测（新进程，跨会话）：

```
你> 我昨天做了什么？        → 昨天你去跑了10公里…还遇到老朋友张三
你> 关于跑步我都记了什么？  → 关于跑步，你目前只记了一条…
你> 一共记了几条？         → 2 条：1 条经历、1 条感受
```

**已知限制**：当前是关键词 + 标签检索，模糊描述（"那次很累的跑步"）效果有限；语义检索待接本地向量库。

## 5. 时间对齐 TimeAligner（接口预留）

桥接客观指标与主观事件，**靠时间窗，不靠内容相似度**——两类数据本来就没语义可比性。

核心场景："上次跑 10 公里那天我感觉怎么样？"

```
1. 查 MetricStore：找到符合条件的活动 → 得到 occurred_at（如 11月15日 7:10）
2. 定时间窗：以活动时间为锚，取前后 N 小时（默认当天，可配）
3. 查 EventStore：该窗口内的事件（"跑完很畅快""下午开会很累"）
4. Agent 合并归纳：客观数据 + 主观感受 → 完整回答
```

反向也支持："特别累的日子睡得怎么样" → 先查 `mood=疲惫` 的事件 → 用时间窗去 MetricStore 查当天睡眠 / 心率。

```python
class TimeAligner(Protocol):
    def align_by_metric(self, metric_query: str, window_hours: int = 24) -> list[tuple]: ...
    def align_by_event(self, event_query: str, window_hours: int = 24) -> list[tuple]: ...
```

对齐结果只在查询时组合，不强制物理写回；`metric_refs` 是可选的加速 / 追溯字段。

## 6. MetricStore 与 Digest

**MetricStore**（客观数据，Phase 2 已实现）：单张 `metrics` 表 + `kind` 分区，`(kind, source_id)` 唯一约束做幂等 upsert，payload 保留佳明原始 JSON；11 类抓取器覆盖活动、睡眠、日摘要、步数、HRV、心率、压力、身体电量、体重、健身年龄（清单见 `src/assistant/sport/sync.py` 的 `FETCHERS`）。数据经 Garmin 官方 Personal API 同步（详见 `07-Garmin-Personal-API-调试报告.md`）。落地在独立 `metrics.db`，与事件库物理分离。入口：同步 `scripts/sync_garmin.py`、查询 `scripts/query_metrics.py`；当前不接对话、不做 Agent 工具。

| 字段 | 说明 |
|---|---|
| id / kind / source_id | 稳定 ID（如 `activity:12345`）、类型、佳明原始 ID |
| start_time / end_time | 时间锚点，用于与事件对齐 |
| payload | 佳明原始返回 JSON + 提取的查询字段（如 `_distance_km`） |
| synced_at | 最近同步时间；游标单独存 meta 表 |

所有指标都有 `start_time` 作为与事件对齐的时间锚点。

**Digest**（派生总结，Phase 3）：

```python
class Digest(BaseModel):
    id: str
    period: str                  # week | month | year
    start: datetime
    end: datetime
    content: str                 # 聚合后的总结文本
    event_ids: list[str]         # 来源事件，可回溯
    metric_ids: list[str]        # 来源指标，可回溯
    created_at: datetime
```

Digest 生成后**作为 `type=summary` 的事件**写回 EventStore，可被再次检索、总结——形成复利。

## 7. 存储策略与选择性同步

### 7.1 本地优先

- 所有数据默认留本地 `data/`（已 gitignore）。
- EventStore 与 MetricStore 可同处一个 `.db` 文件，但**分表、分接口、分生命周期**——逻辑完全分离。
- 正式库 `data/events.db` 目前为空（还没正式使用）；端到端测试用的是临时库 `/tmp/pa_e2e_data/events.db`。

### 7.2 选择性同步（默认关）

```python
class SyncPolicy(BaseModel):
    allowed_sources: list[str] = []
    min_importance: float = 0.0
    excluded_tags: list[str] = []
    sync_metrics: bool = False
    enabled: bool = False          # 总开关，默认关闭
```

两套数据可分别配置：生活感受更敏感，默认更保守；运动数据相对不敏感。`SyncBackend` 只定义接口，不实现。

## 8. 风险与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| 自动记录误记 / 漏记 | 判定模型可能判断错 | 保守判定；事件可删改；调试期可关 |
| 抽取成本 | 每轮多一次模型调用 | 轻量模型 / 异步；成本计入 Provider 层（当前 route 到主模型） |
| 重复事件 | 同一件事记多次 | 同标题 24h 去重 |
| 检索不准 | 模糊描述搜不到 | 当前关键词 + 标签；未来接向量语义检索 |
| 时间对齐窗口不当 | 太大引入无关事件，太小漏掉 | 窗口可配，默认当天；回答时展示时间便于校准 |
| 事件膨胀 | 长期数据量大 | 按时间分区；Digest 后归档原始事件 |
| 隐私 | 生活细节敏感 | 本地优先、同步默认关、敏感标签排除、可删任意事件 |
| 时间准确性 | 对话里"昨天"要正确解析 | 以当前时间为参考推断 `occurred_at` |

## 10. 下一步建议
