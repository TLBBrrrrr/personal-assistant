## 1. 定位：三类数据，分开存

之前只有 mem0，它做的是**事实抽取**——"你喜欢晨跑"这类偏好，有损压缩、无时间维度，撑不起"记录事情 + 总结回忆"。经过讨论，明确要记的其实是**三类本质不同的数据**，必须分开存：

| 类别 | 内容 | 谁生成 | 特征 | 存储 |
|---|---|---|---|---|
| **A. 事实** | 稳定偏好、身份、长期习惯 | 人（对话中表达） | 有损可接受、无时间维度 | mem0 |
| **B. 客观运动数据** | 佳明活动、睡眠、心率、步数 | 机器（Garmin） | 结构化、高频、量大、字段固定 | **MetricStore（SQLite 业务表）** |
| **C. 主观生活感受** | 经历、感受、想法、决定、人际 | 人（对话中表达） | 语义化、低频、量小、需回溯 | **EventStore（事件日志）** |

**为什么要分开 B 和 C**（关键决策）：

| 维度 | B 运动数据 | C 生活感受 |
|---|---|---|
| 生成方 | 机器自动同步 | 人主动表达 |
| 结构 | 字段固定，可聚合统计 | 自由文本，需语义检索 |
| 频率量级 | 每天几十条 | 每天几条 |
| 索引方式 | 时间 + 类型 + 数值范围 | 向量 + 全文 + 标签 |
| 清理策略 | 原始数据可定期归档 | 长期珍藏 |
| 向量化 | 没必要，浪费 | 必要，支撑语义检索 |

塞进一个事件流的后果：海量运动数据淹没感受、无意义的向量化开销、清理策略互相绑架。**分开存是对的决定。**

**但"关联性不大"不等于"完全无关"**——存在一种典型需求：把客观数据和当时感受在时间轴上对上。比如"上次跑10公里那天我感觉怎么样"。所以设计一层**时间对齐查询**桥接两者，而不是让它们老死不相往来。

整体记忆分层：

| 层 | 名字 | 管什么 | 典型问题 | 实现 |
|---|---|---|---|---|
| L1 | 短期上下文 | 本轮对话消息 | "刚才说了什么" | 会话内 messages，不落库 |
| L2 | 事实记忆 | 稳定事实偏好 | "你是谁、喜欢什么" | mem0（接口可替换） |
| L3a | 客观指标 | 运动/健康结构化数据 | "上周跑了多少" | MetricStore（SQLite） |
| L3b | 生活事件 | 经历、感受、想法 | "发生了什么、我当时怎么想" | EventStore（本设计重点） |
| 桥接 | 时间对齐 | 按时间窗关联 L3a 与 L3b | "跑步那天的感受如何" | TimeAligner |
| 派生 | 总结 | 聚合上述数据 | "这个月过得怎么样" | Digest（回写为事件） |

## 2. 数据模型

### 2.1 Event（生活事件与感受）——EventStore 核心结构

```python
from datetime import datetime
from typing import Any

class Event(BaseModel):
    id: str                      # 唯一 ID
    occurred_at: datetime        # 事件发生时间（不是记录时间）
    recorded_at: datetime        # 写入系统的时间
    source: str                  # 来源：dialogue | manual | digest | system
    type: str                    # 类型：experience | feeling | note | decision | milestone | summary
    title: str                   # 一句话标题，"跑完10公里很畅快"
    content: str                 # 正文，自然语言的经历/感受描述
    tags: list[str]              # 主题标签，["跑步", "心情", "工作"]
    entities: list[str]          # 相关实体，["同事张三", "项目X"]
    mood: str | None             # 情绪标签，可选，"开心" | "疲惫" | "平静"
    importance: float            # 0-1，重要度，驱动总结筛选
    metric_refs: list[str]       # 关联的客观数据 ID（可选，时间对齐时生成）
    embedding_ref: str | None    # 向量库引用，语义检索用
```

设计要点：

- **source 不含 garmin**：佳明数据不进事件日志，它进 MetricStore。事件里只通过 `metric_refs` 留存关联指针。
- **去掉 payload**：结构化原始数据 belongs to MetricStore，不在事件里双份保存。
- **occurred_at 与 recorded_at 分开**：补记、导入历史数据时两者不同。
- **mood 显式建模**：感受类事件的高频查询维度，比纯文本检索更直接。
- **importance 驱动总结**：优先取高重要度事件，避免流水账。

### 2.2 Metric（客观运动数据）——MetricStore 结构

沿用总体设计的三张业务表，独立存放，不进 EventStore：

| 表 | 关键字段 |
|---|---|
| Activity | id, type, start_time, duration, distance, calories, avg_hr, max_hr, pace |
| Sleep | id, date, duration, deep, light, rem, awake, score |
| DailyMetric | id, date, steps, resting_hr, weight, body_fat |

统一时间字段：所有指标都有 `start_time` 或 `date`，作为与事件对齐的锚点。ID 可被事件的 `metric_refs` 引用。

### 2.3 Digest（派生总结）

```python
class Digest(BaseModel):
    id: str
    period: str                  # week | month | year
    start: datetime
    end: datetime
    content: str                 # 聚合后的总结文本
    event_ids: list[str]         # 来源事件，可回溯
    metric_ids: list[str]        # 来源指标，可回溯
    created_at: datetime
```

Digest 生成后**作为 `type=summary` 的事件**写回 EventStore，可被再次检索、总结——形成复利。

## 3. 自动记录机制

你选的是"对话随口记 + 领域数据自动汇总"，两条路径写入**不同的存储**。

### 3.1 对话随口记 → EventStore

每轮对话结束后挂后处理，判断并落库：

```
用户说话 → Agent 回复 → [post-turn hook]
                            ├─ 重要性判定：这轮有没有值得记的经历/感受？
                            ├─ 是 → 抽取成 Event（LLM 结构化输出 + Pydantic 校验）
                            ├─ 时间解析：把"昨天/上周"解析为 occurred_at
                            ├─ 去重：与近期相似事件比对
                            └─ 落库 → EventStore
```

关键设计：

- **不是每句都记**：先判定，过滤寒暄、重复、纯问答；小模型或轻量规则，控制成本。
- **抽取走结构化输出**：PydanticAI 强项，让模型按 `Event` 模型输出，天然类型校验。
- **时间解析**：对话里的相对时间以当前时间为参考推断，校验合理性。
- **失败不打断对话**：后处理异步，抽取失败只记日志。
- **可关闭**：配置开关，调试期可关闭观察效果。

**值得记**（默认规则，可配置）：

- 经历、决定、计划、情绪感受（泛生活，不限运动）
- 提到具体时间/地点/人物的事实
- 里程碑事件
- 用户纠正的信息（同时更新 mem0）

**不记**：纯知识问答、寒暄、助理自己说的话、高度重复内容。

### 3.2 自动汇总 → MetricStore

佳明数据同步后写入**独立的指标表**，不生成事件：

```
Garmin 同步完成 → sport 适配器 → 结构化数据 → MetricStore（Activity/Sleep/DailyMetric）
                                  └─ 不做向量化、不进 EventStore
```

领域接入统一走接口：

```python
class MetricEmitter(Protocol):
    def emit(self, raw: Any) -> list[Metric]: ...   # 原始数据 → 指标记录

class EventEmitter(Protocol):
    def emit(self, messages: list[dict]) -> list[Event]: ...   # 对话 → 事件
```

两套 emitter 各司其职：客观数据走 MetricEmitter，主观表达走 EventEmitter。

## 4. 回忆与查询怎么支撑

你要的四种回忆方式，加上跨存储的时间对齐：

| 需求 | 检索路径 | 落地工具 |
|---|---|---|
| **随时问随时查** | EventStore 语义检索（向量）+ 全文（FTS5）+ 时间过滤 | `recall(query, time_range, limit)` |
| **按主题回顾** | EventStore 按 `tags`/`entities` 过滤 + 语义补充 | `recall_topic(topic, time_range)` |
| **定期自动总结** | 聚合 EventStore + MetricStore → LLM 归纳 → 生成 Digest | `digest(period)` + 定时任务 |
| **时间线浏览** | 按 `occurred_at` 排序分页，可叠加当日指标摘要 | `timeline(start, end, page)` |
| **跨存储对齐**（新增） | 时间窗关联：指标锚点 → 同窗口事件 → Agent 合并 | `aligned_recall(metric_query, window)` |

### 4.1 时间对齐（TimeAligner）怎么工作

核心场景："上次跑10公里那天我感觉怎么样？"

```
1. 查 MetricStore：找到符合条件的活动 → 得到 occurred_at（如 11月15日 7:10）
2. 定时间窗：以活动时间为锚，取前后 N 小时（默认当天，可配置）
3. 查 EventStore：该窗口内的事件（如"跑完很畅快""下午开会很累"）
4. 回填关联：把 metric_id 写入这些事件的 metric_refs（可选）
5. Agent 合并归纳：客观数据 + 主观感受 → 完整回答
```

反向也支持："我那些特别累的日子运动数据怎么样？" → 先查 EventStore 里 `mood=疲惫` 的事件 → 用时间窗去 MetricStore 查当天睡眠/心率。

设计原则：

- 对齐靠**时间窗**，不靠数据内容相似度——两类数据本来就没语义可比性。
- 窗口大小可配置（当天 / ±N 小时），默认当天。
- 对齐结果只是查询时组合，不强制物理写回；`metric_refs` 是可选的加速/追溯字段。

几个细节：

- 前四种都注册成 Agent 工具，对话里直接问就能触发。
- 时间线浏览在 CLI 阶段输出格式化列表，未来渲染成日历/时间轴。
- 精确名字/术语靠全文检索，模糊描述（"那次很累的跑步"）靠向量检索。

## 5. 存储与选择性同步

### 5.1 本地存储结构（两套分开）

**EventStore 侧：**

| 存储 | 内容 | 技术 |
|---|---|---|
| SQLite `events` 表 | 生活事件结构化字段 | `sqlite3` |
| FTS5 全文索引 | 关键词检索 | SQLite 内置 |
| 标签/实体/情绪索引 | 主题与情绪过滤 | 关联表 |
| 向量库 | 语义检索 | 本地向量库（Phase 1B 选型，优先轻量方案） |

**MetricStore 侧：**

| 存储 | 内容 | 技术 |
|---|---|---|
| SQLite `activities` / `sleep` / `daily_metrics` | 佳明客观数据 | `sqlite3`，按时间建索引 |
| 增量同步游标 | 上次同步时间戳 | SQLite 配置表 |

两库物理可同处一个 `.db` 文件但**分表、分接口、分生命周期**——逻辑上完全分离，不互相干扰。

### 5.2 选择性同步

- **默认全部留本地**，不主动上传。
- `SyncPolicy` 按 `source` / `type` / `importance` / `tags` 决定哪些事件可同步：
  ```python
  class SyncPolicy(BaseModel):
      allowed_sources: list[str] = []        # 允许同步的来源
      min_importance: float = 0.0            # 重要度阈值
      excluded_tags: list[str] = []          # 排除的敏感标签
      sync_metrics: bool = False             # 客观指标是否同步（默认否）
      enabled: bool = False                  # 总开关，默认关闭
  ```
- 两套数据可分别配置同步策略：生活感受更敏感，默认更保守；运动数据相对不敏感，可单独放行。
- `SyncBackend` 接口抽象，本期只定义不实现。

## 6. 接口定义

```python
from typing import Protocol, AsyncIterator

class EventStore(Protocol):
    async def append(self, event: Event) -> str: ...
    async def append_many(self, events: list[Event]) -> list[str]: ...
    async def update(self, event_id: str, patch: dict) -> None: ...
    async def search(self, query: str, time_range: tuple | None = None,
                     tags: list[str] | None = None, limit: int = 10) -> list[Event]: ...
    async def by_topic(self, topic: str, time_range: tuple | None = None) -> list[Event]: ...
    async def timeline(self, start: datetime, end: datetime,
                       page: int = 0, size: int = 50) -> list[Event]: ...
    async def iter_range(self, start: datetime, end: datetime) -> AsyncIterator[Event]: ...
    async def delete(self, event_id: str) -> None: ...
    async def stats(self) -> dict: ...

class MetricStore(Protocol):
    async def upsert(self, metric: Metric) -> str: ...
    async def query(self, kind: str, start: datetime, end: datetime,
                    filters: dict | None = None) -> list[Metric]: ...
    async def latest(self, kind: str) -> Metric | None: ...
    async def sync_cursor(self) -> datetime | None: ...
    async def set_sync_cursor(self, ts: datetime) -> None: ...

class TimeAligner(Protocol):
    async def align_by_metric(self, metric_query: str, window_hours: int = 24) -> list[tuple[Metric, list[Event]]]: ...
    async def align_by_event(self, event_query: str, window_hours: int = 24) -> list[tuple[Event, list[Metric]]]: ...

class EventExtractor(Protocol):
    async def extract(self, messages: list[dict]) -> list[Event]: ...

class DigestGenerator(Protocol):
    async def generate(self, period: str, start: datetime, end: datetime) -> Digest: ...
```

## 7. 对分阶段路线的影响

| 阶段 | 调整 |
|---|---|
| **Phase 0** | 预留 `EventStore`、`MetricStore` 接口定义；对话循环留 post-turn hook 挂点 |
| **Phase 1A** | mem0 事实记忆 |
| **Phase 1B** | EventStore + 对话随口记 + `recall` 工具（主观感受） |
| **Phase 2** | Garmin 同步 → **MetricStore**（不生成事件）；运动查询工具 |
| **Phase 3** | Digest 总结 + 时间线浏览 + **TimeAligner 跨存储对齐** + 主题回顾 |
| **Phase 4–5** | 不变 |

**Phase 1B 验证**：

1. 对话说"昨天去跑了10公里，感觉特别爽" → EventStore 生成一条感受事件
2. 隔一轮问"我昨天干嘛了" → `recall` 能答出
3. 问"关于跑步我都记了什么" → 主题回顾返回相关事件
4. 纯寒暄"你好" → 不产生事件

**Phase 3 对齐验证**：

1. 说"上次跑10公里那天感觉怎么样" → TimeAligner 先查活动锚点，再查同日感受事件，合并回答
2. 说"特别累的那些日子睡得怎么样" → 反向对齐，EventStore 找疲惫事件 → MetricStore 查当日睡眠

## 8. 风险与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| 自动记录误记/漏记 | 判定模型可能判断错 | 规则+模型结合；事件可删改；调试期可关闭 |
| 抽取成本 | 每轮多一次 LLM 调用 | 轻量模型判定；批量/异步；成本计入 Provider 层 |
| 重复事件 | 同一件事记多次 | 写入前相似度比对，重复则合并或跳过 |
| 时间对齐窗口不当 | 窗口太大引入无关事件，太小漏掉 | 窗口可配置，默认当天；查询时展示时间便于校准 |
| 事件膨胀 | 长期数据量大 | 按时间分区；Digest 后归档原始事件；FTS5 + 向量索引 |
| 隐私 | 生活细节敏感 | 本地优先、同步默认关、敏感标签排除、可删任意事件 |
| 时间准确性 | 对话里"昨天"要正确解析 | 以当前时间为参考推断 occurred_at，校验合理性 |
